# Gate

When a workspace coordinator says a change is ready:

1. **Get one handoff:** the candidate revision and base, the frozen diff, what ran on which build, what's still pending, open findings, a Patterns line (what older code got better, what was found and left), and the decision needed. Proof counts only for the revision and build it ran on.
   If the change affects a shared interface, replay the affected caller on the candidate built against its intended base. If that base is still pending, name the check that must pass before this change can land.
2. **Read the diff against the base it will land on** while its checks run. Check the behavior and the design: does it duplicate something that already exists, and would it be fine if the next twenty agents copied each new construct? They will.
3. **Over about 300 lines,** also give the frozen diff to one read-only subagent from a model family the reviewers didn't use, with two instructions: for each construct the diff adds, grep the base and report where its count goes from one to two; and trace what the change stores (keys, files, settings), key by key, against the base. Fault reviews miss what this finds, like one fact stored in four places. Verify each finding in the code before acting on it.
4. **Decide in one message:** blocked on a named issue, or a go with its conditions named: the revision, the checks still owed, the PR owner, and what the user's grant covers. A conditional go saves a round trip: "Go on a new head that reads `RefusedError.code` instead of parsing the message; it carries once typecheck and the sync tests pass on that head."
5. **After the go,** the PR owner opens the PR, watches CI and review (`az-greenlight-pr` if installed), and merges under the grant. A fix for a CI or review finding keeps the go if a check that failed before the fix passes after it and the full gate ran on the new head; the coordinator sends you the delta with its merge report. Anything more comes back to you before merge.
6. **After the merge,** get the merge SHA so the next coordinator can rebase. If the user's goal is working software rather than a merged PR, track merged, released and verified live as three separate states, and close the item only when the original failing journey works on the released build.
