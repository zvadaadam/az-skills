# Gate

**Before the handoff.** When a lane over about 300 lines first freezes a candidate (its lead sends you the revision in one line), start one read-only subagent from a model family the lane's reviewers don't use, alongside the lane's own reviewer. Give it the frozen diff and two instructions: for each construct the diff adds, grep the base and report where its count goes from one to two; and trace what the change stores (keys, files, settings), key by key, against the base. Verify each finding in the code, then send the findings into that review round. Fault reviews miss what this finds, like one fact stored in four places, and found this early it costs one round instead of several: a lane that got it only at its handoff needed six more candidates.

When a lead says a change is ready:

1. **Get one handoff:** the candidate revision and base, the frozen diff, what ran on which build, what's still pending, open findings, a Patterns line (what older code got better, what was found and left), and the decision needed. Proof counts only for the revision and build it ran on.
2. **Read the diff against the base it will land on** while its checks run; after the early read, read only what changed since. Check the behavior and the design: does it duplicate something that already exists, and would it be fine if the next twenty agents copied each new construct? They will.
3. **Decide in one message:** blocked on a named issue, or a go with its conditions named: the revision, the checks still owed, the PR owner, and what the user's grant covers. A conditional go saves a round trip: "Go on a new head that reads `RefusedError.code` instead of parsing the message; it carries once typecheck and the sync tests pass on that head."
4. **After the go,** the PR owner opens the PR, watches CI and review (`az-greenlight-pr` if installed), and merges under the grant. A fix for a CI or review finding keeps the go if a check that failed before the fix passes after it and the full gate ran on the new head; the lead sends you the delta with its merge report. Anything more comes back to you before merge.
5. **After the merge,** get the merge SHA so the next lead can rebase, and leave the after-merge bookkeeping (issue tracker, follow-up reports) to each lead. If the user's goal is working software rather than a merged PR, track merged, released and verified live as three separate states, and close the item only when the original failing journey works on the released build.
